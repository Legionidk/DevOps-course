# Работа К3-01

- Группа: ИТ-9.24.1-ФЭ

Для проекта используется упрощенная модель CI/CD, так мы легко автоматизируем проверку изменений и подготовку приложения к выпуску.

## Последовательность:

1. Разработчик пушит изменения в свою рабочую ветку
2. Как только разраб делает PR в `main`, запускаются проверки
3. CI тестит приложение
4. Если тесты успешные - запускается сборка Docker
5. После успешной сборки приложение считается готовым к выпуску
6. Уже в ручном режиме мы принимаем решение о выпуске

## Схема ветвления

```
Изменение в рабочей ветке
|
PR в main 
|
тесты прошли? -> merge в main
тесты НЕ прошли? -> ошибка -> исправление -> повторный PR
```

## Сравнение с git-flow

Git-flow предполагает более сложную структуру ветвления, включающую в себя долгоживущие `develop`/`release`-ветки. Там вообще и другие еще могут быть в целом. Для нас это несколько избыточно, поэтому у нас попроще чутка. У нас меньше веток, более простой процесс, интеграция быстрее (в теории)

## Обратная связь об ошибках

Обратная связь появляется во время PR, а точнее во время проверок после PR. Если тесты обнаруживают проблему, GitHub Actions отмечает запуск как провальный. Разработчик может ознакомиться с логами и исправить ошибку. Так ошибки не попадают в `main`

## Является ли сборка образа автоматически deployment?

Нет. Сборка - подготовка артефакта, который можно использовать для последующего развертывания. Deployment предполагает, что этот образ будет запущен в целевой среде. На сервере том же.
